## 尺寸约束不只是一条 `width`

浏览器计算 box 尺寸时，不是读取一条 `width` 就结束。先把它当作一个需要多项输入的过程：内容提供 intrinsic size，作者提供 preferred/min/max constraints，containing block 提供可用空间。

<Concept title="从内容、约束与 containing block 一起推理">
`width` / `height` 更接近 preferred size，而不是“最后一定会画出的尺寸”。内容本身可能需要更宽的空间，也可能在有换行机会时缩小；`width: auto` 也不是没有尺寸，而是把决定过程交给当前 formatting context。

`min-width` / `min-height` 是下限，`max-width` / `max-height` 是上限。它们不是 `width` 的别名：preferred size、最小值和最大值可以同时存在，最终 used size 要在这些约束与可用空间之间求解。最小约束不能被最大约束压穿。

当内容或约束超出 box 能容纳的空间时，问题进入 overflow。`visible` 允许内容绘制到 box 外，`auto` 在需要时提供滚动机制，`hidden` 裁剪并隐藏滚动界面。`hidden` 是一个具体的呈现选择，不是把错误尺寸假设修好的万能开关。
</Concept>

“让内容参与尺寸决定”故意使用足够宽的 locked frame 与高 specificity 的既有 `#intrinsic-demo .label` 规则。starter 的 block-level `width:auto` 会铺满 frame 的可用内容宽度；改成 `width:max-content` 后，背景/outline 会明显收缩到内容的最大 intrinsic inline size。Checker 用 `rule-style` 证明 learner 保留现有 sizing context 并 authored `width:max-content`，同时用 computed display、locked fixture width/box-sizing 与水平 layout evidence 防止常见 cascade、隐藏或 fixture 改写把预览对比架空。它仍不是通用 cascade prover，也不把某个固定像素宽度当作 intrinsic size 的定义。

“修复固定宽度失败”用两个锁定 containing block 验证同一条 learner rule：窄 frame 中头像必须被 `max-width: 100%` 约束且保持在 content box 内，宽 frame 中实际宽度仍应为 320px。源码检查同时确认 `width: 320px` 与 `max-width: 100%` 的 authored intent。这样不会把窄容器中的正确缩小判错，也不会让通用的固定 used-width override 仅靠碰巧等于当前窄 fixture 宽度过关。

这仍不是“无法作弊”的通用 cascade 证明：刻意针对 locked fixture 结构编写特殊规则超出本练习的正常解题路径。当前证据组合负责验证正常课程路径中的源码意图、受控布局结果和可见学习对比；它不支持任意 cascade 证明、纵向包含、绘制遮挡或多视口响应式行为。`choose-overflow-strategy` 当前的声明检查仍不能证明滚动条真的出现或内容确实发生 overflow；预览观察仍是学习的一部分，本课不因局部 checker 改进而自动发布。
