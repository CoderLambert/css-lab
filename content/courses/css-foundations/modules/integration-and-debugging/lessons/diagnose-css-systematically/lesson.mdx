## “没有生效”是 pipeline 中的某一阶段出了问题

CSS 的结果不是由某一条 declaration 单独决定的。先确认 selector 是否命中，再确认 cascade winner；如果某个 property 没有 cascaded value，还要进入 defaulting，判断它是继承 parent 的 computed value 还是使用 initial value。得到 specified value 后，浏览器再继续解析 computed/used value，并把结果交给当前 formatting context、sizing constraints、positioning context 或 viewport condition。调试时应沿着因果链缩小范围，而不是不断添加更大的 selector 或更大的 `z-index`。

<Concept title="从 selector 到 environment 的 debugging pipeline">
把“CSS 没生效”拆成八个可检查的阶段：

1. selector 是否匹配了目标元素？
2. 匹配的 declarations 中，哪条在 cascade 中胜出？在本课程范围内重点看 importance、specificity 与 source order；inheritance 不是用来给两条 competing declarations 排名的 cascade 因子。
3. 如果这个 property 没有 cascaded value，defaulting 如何得到 specified value？默认继承的 property 会取 parent 的 computed value，默认不继承的 property 会使用 initial value；`inherit`、`initial`、`unset`、`revert` 等 CSS-wide keyword 会显式改变 defaulting 行为。
4. 浏览器最终解析出了什么 computed/used value？`width: 100%`、`max-width`、字体度量或 shorthand 的结果不能只靠 source text 猜。
5. 需要的 formatting context 是否真的建立？例如 Flex/Grid 规则要求对应的 container context；normal flow 也始终在工作。
6. sizing、intrinsic size 或 overflow constraint 是否改变了可见结果？固定 width 可能超过 containing block，min/max 也可能限制它。
7. 是否有 containing block、stacking context、scroll context 或 positioned ancestor 参与？声明存在不等于最终 paint/scroll outcome 已被证明。
8. 是否有 media query 或其他 viewport/environment condition 控制这条规则？先确认条件，再判断命中的 cascade。

这条顺序来自前面各 Module 的 mental model，也符合 MDN 的 CSS debugging guidance：先观察实际命中的规则和浏览器结果，再回到对应的 CSS 机制。它是迁移用的思考框架，不要求每次都机械打开同一组 DevTools 面板。
</Concept>
